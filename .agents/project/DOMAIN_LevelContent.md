# Remote level content

## Ownership and loading
- Chapter order resolves `Assets/Game/Levels/ChapterData.cs` addresses against the existing flat loading catalog. Chapter mode retains downloaded levels for cyclic replay and ignores legacy final-level eviction; investigation holds separate, bounded clue-image asset handles. See [.agents/project/DOMAIN_Chapters.md](.agents/project/DOMAIN_Chapters.md).
- `Assets/Game/Levels/LevelData.cs` embeds search sprites/stages and level time. Every playable level requires `SearchData.MainImage`; chapters also require `SearchData.ClueImage`. There is no puzzle fallback. See [.agents/project/DOMAIN_Anomalies.md](.agents/project/DOMAIN_Anomalies.md).
- `Assets/Game/Gameplay/LevelsManager.cs` loads `LevelsData.Levels[].LevelId` through `Assets/Game/AssetManagement/AddressablesAssetSystem.cs`, then gets the `LevelData` by the same key. `Assets/Game/Gameplay/LevelContentSystem.cs` downloads/reserves content by that key. Addressables label `Level` indexes levels for cache ownership.
- `Assets/Game/Levels/Editor/LevelReferenceDrawer.cs` discovers selectable addresses from the `Levels` Addressables group. Registration makes a level selectable; it does not append it to the authored progression in `Assets/Game/Levels/LevelsData.asset`.

## Preparation progress
- `Assets/Game/Initialization/GameStartupProcessor.cs` opens `Assets/Game/UI/Windows/PreloadWindow/PreloadWindow.prefab` before loading `LevelsData`. It shares a fresh `Assets/Game/UI/Windows/PreloadWindow/PreloadWindowModel.cs` with `Assets/Game/Gameplay/GameplaySystem.cs`. Later preparations omit the model and do not open a preload window.
- `Assets/Game/Gameplay/GameplaySystem.cs` (`PrepareGame`) always awaits required content and level initialization before returning. It never opens a preload window; only when startup supplies its model does it report progress and close the initial window. For startup, catalog loading occupies 0–10%, completed startup setup reaches 15%, and required level preparation occupies 15–95%. It marks 100% only after level initialization succeeds and the prepared session is paused, then yields a frame before closing. Existing announcement/preview/tutorial presentation remains in `StartGame` after closing.
- Within level preparation, `Assets/Game/Gameplay/LevelsManager.cs` allocates 50% to required content availability, 35% to loading assets/scenes and 15% to runtime initialization. Unmeasured setup advances only when completed; these ranges are stage weights, not elapsed-time estimates. Background reserve downloads do not affect readiness.
- `Assets/Game/AssetManagement/AddressablesCacheController.cs` reports `GetDownloadStatus().Percent` while awaiting the retained dependency operation; zero missing bytes completes immediately. `Assets/Game/AssetManagement/AddressablesAssetSystem.cs` accepts optional `IProgress<float>` for loads/downloads. Loading averages five resource groups and operation progress within each group; empty/cached groups complete without synthetic animation. Ownership/release policy is unchanged.
- The preload model clamps ordinary reports below 100% and suppresses decreases (including retries); only `Complete` reaches 100%. The passive view binds/unbinds its event and writes the horizontal fill directly. `Assets/Game/UI/Windows/General/WindowSystem.cs` supports opt-in `Open(..., refreshModel: true)` to reset an already open preload window for a new preparation; other callers retain existing behavior.

## Remote configuration and authoring
- `Assets/AddressableAssetsData/AddressableAssetSettings.asset` has the authored `Remote` profile, `ContentBranch`, `Remote.BuildPath` and `Remote.LoadPath`. Build and load paths both include the branch and platform. Preserve these values; do not replace them with localhost or strip the branch.
- `Assets/Game/AssetManagement/Editor/LevelContentBuildController.cs` exposes `Game/Content/Configure Remote Levels` and `Game/Content/Build Remote Levels`. Configuration requires the authored profile/paths, registers all `LevelData` assets under `Assets/` in `Levels`, preserves existing addresses and rejects duplicate/empty addresses. New addresses use asset names; the `Level` label and address/label catalog inclusion are required.
- The controller configures `Levels` and `Level Shared` for remote separately packed, cached bundles. Shared dependencies also used by local content remain in the default local group; remote-only shared dependencies use `Level Shared`. Source assets/GUIDs stay in place.
- `Assets/Game/Levels/Editor/LevelCreator.cs` exposes `Game/Create Level`. It prepares the existing remote setup, chooses a free `LevelN` folder/address, creates an anomaly-level asset with empty search configuration, persists remote registration and selects the asset. It opens `Assets/Game/Levels/Editor/AnomalyLevelEditorWindow.cs` for main/clue images, whole anomaly layers and stages; see `.agents/project/DOMAIN_Anomalies.md`. It no longer creates puzzle data or opens the slicer. Gameplay progression order is preserved.
- Remote catalog updates on startup remain disabled by the existing setup. The player includes its catalog; downloaded bundles still use the authored server URLs. Building content alone does not upload it; upload is the automatic publication below.

## Automatic SFTP publication (Editor only)
- Code: `Assets/Game/AssetManagement/Editor/Publishing/` (assembly `Game.AssetManagement.Publishing`, tests in `Assets/Game/AssetManagement/Editor/Publishing/Tests/`). Entry: `RemoteContentPublishSystem.cs`; hooks: `RemoteContentPublishPlayerProcessor.cs` (BuildPlayerProcessor order 0, opens a run before the Addressables processor, order 1), `RemoteContentPublishHooks.cs` (subscribes `BuildScript.buildCompleted`, attaches only `AddressablesPlayerBuildResult` to the open run) and `RemoteContentPublishPostprocessor.cs` (IPostprocessBuildWithReport). Publication never builds Addressables.
- `RemoteContentPublishGate.cs` allows publication only for a succeeded Android .apk/.aab file (no Gradle export) written after the run started, built by the same Build Profile GUID that is explicitly enabled, with an error-free Addressables player build result from the same run. Other profiles never publish.
- Output comes from the active profile (`AddressablesOutputResolver.cs`: remote group `BuildPath`/`LoadPath` and remote catalog paths) filtered by the current build's `FileRegistry`; `RemoteContentPlanBuilder.cs` publishes only `*.bundle`, `catalog*.json|bin`, `*.hash`. Subfolders below each build path are kept; `RemoteContentPathMapper.cs` maps the load URL onto the FileZilla destination root without duplicating shared segments. `RemoteLoadPath` is never changed.
- Order: bundles, catalog, `.hash`; every file uploads to `<name>.<token>.uploading` and is renamed after success (a same-named target is replaced only if the server refuses overwrite). First failure stops later stages; old remote files are never deleted. After upload, the `.hash` is downloaded over HTTPS and compared; mismatch/error = incomplete. Failure is logged as «APK/AAB создан, НО публикация НЕ завершена».
- Transport: WinSCP .NET assembly of a local WinSCP install, loaded by reflection (`WinScpSftpSession.cs`, not exercised against a real server). Settings: Project Settings > Remote Content Publishing (`ProjectSettings/RemoteContentPublish.asset`, no secrets). Secrets: env `WHATHAPPENED_SFTP_PASSWORD`/`WHATHAPPENED_SFTP_HOST_KEY` or a per-user file outside the project (`%APPDATA%/WhatHappened/RemoteContentPublish.secrets.json`, plain text). «Проверить подключение» only opens a session and lists the destination.

## Focused validation
- Compile in the existing Unity editor, run the existing remote content build menu, and inspect the actual build result/console.
- Resolve every level address as `ScriptableObject`/`LevelData` in the built catalog, check the `Level` label and authored progression references, and verify level bundle dependencies use the evaluated remote URL.
- For creation checks, use the menu's asset-creation core with an exclusive disposable Unity folder, inspect persisted search data and remote entry, build and resolve its address, then remove its temporary registration and restore the production-only catalog. Leave disposable files to managed cleanup.
- A successful Android Addressables build and catalog resolution do not prove that generated files have been uploaded or that the server serves them. Publication tests use in-memory fakes only; real SFTP/WinSCP, real hosting and a real Build Profile build remain manual checks.
