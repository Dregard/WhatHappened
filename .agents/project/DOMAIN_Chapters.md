# Chapter progression and clues

## Ownership and setup
- `Assets/Game/Levels/LevelsData.cs` embeds ordered `ChaptersArray` using `Assets/Game/Levels/ChapterData.cs`. Each chapter lists `LevelReference` addresses in play order and existing `RewardData` assets in `RewardsList`. Addresses must also exist in the existing flat `Levels` loading catalog. Empty chapter configuration retains legacy progression; empty individual chapters and unknown addresses are rejected.
- Each chapter level must have both `SearchData.MainImage` and `SearchData.ClueImage` in `Assets/Game/Levels/LevelData.cs`. The clue remains authored once in the level. `Assets/Game/Gameplay/LevelsManager.cs` rejects chapter levels missing either image before gameplay initialization. Old production puzzle levels were removed; the production anomaly/chapter catalog remains empty until authored.
- `Assets/Game/Gameplay/GameplayProgressController.cs` owns chapter rules in the existing `GameplayProgress` profile (`Assets/Game/Gameplay/GameplayProgressProfile.cs`): monotonically advancing chapter iteration, found prefix count, pending level victory and chapter reward claim. No unfinished stage/anomaly state is serialized. One configured level contributes one clue; chapter size is its level count.
- `Assets/Game/Gameplay/Chapters/ChapterSystem.cs` coordinates clue presentation, investigation snapshots and chapter rewards. `Assets/Game/Initialization/GameplayInstaller.cs` composes it with existing profile/reward/window/HUD services. Passive views are `Assets/Game/Gameplay/Chapters/ChapterHudView.cs` and `Assets/Game/Gameplay/Chapters/ChapterWindow.cs`.

## Completion and restoration
- Completion immediately blocks investigation, including a pending image load, so an investigation cannot replace the required victory screen. The existing search finding/transition acknowledgements release `LevelProgressController.TargetReached`. `Assets/Game/Gameplay/GameplaySystem.cs` awaits `WinSequenceFinished`, then the chapter system fades/holds/flies the level clue into the HUD. Only at flight completion does it commit the clue and completed level progression and call the existing profile save.
- Every chapter level opens `Assets/Game/UI/Windows/WinWindow/WinWindow.prefab`; individual reward/ad and puzzle-combo objects and their runtime logic have been removed. Every search level requires explicit continuation.
- Level victory continuation acknowledges its pending flag and saves. A partial chapter restarts into the next level. A full chapter opens chapter victory next, grants `RewardsList` through `Assets/Game/Purchase/RewardSystem.cs` behind a claim guard, then saves the claim and balances. Window model creation/investigation opening never grants a reward. Current built-in currency/booster processors complete synchronously; continuation waits for their completion.
- On startup, a pending level victory resumes before gameplay; a completed chapter whose level victory was acknowledged resumes chapter victory. Attempt statistics are not persisted, so the restored level screen tolerates missing statistics.
- Chapter continuation requires all clues, level victory acknowledgement and the reward claim. It advances chapter iteration and resets clue count/claim. Chapter selection wraps modulo configured chapter count; each new pass collects anew and can claim anew. Completed chapters have no browsing API/UI.

## UI and resource lifetime
- `Assets/Game/Levels/LevelsData.cs` exposes clue reveal/hold/flight seconds, normalized counter/reveal bounds, chapter colors, grid columns and row height. The investigation grid scrolls vertically and creates exactly one slot per configured level; unfound entries show closed placeholders.
- The chapter system creates its counter under the existing HUD Canvas and a disabled hierarchy-owned window template. `Assets/Game/UI/Windows/General/WindowSystem.cs` registers the template and applies its normal model, sorting, open/close and pause events. Chapter screens use an explicit continuation button rather than Escape dismissal.
- Investigation lazily acquires separate Addressables handles for found levels to read their configured clue sprites. Handles remain bounded to the current prepared chapter UI; cancel/reset removes HUD consumers, releases acquired handles and invalidates late loads. A late load releases its own handle without applying stale state. No entire chapter/catalog is loaded for an empty investigation.
- `Assets/Game/Gameplay/LevelContentSystem.cs` retains downloaded chapter content for cyclic reuse and continues its existing bounded reserve planner; chapter mode does not evict completed levels using legacy final-level loop settings. Resident clue handles are separate from disk retention.
