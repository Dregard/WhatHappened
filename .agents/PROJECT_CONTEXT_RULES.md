# Project context
## Storage and authority
- Follow AGENTS ownership rules. Record actual structure/contracts/setup/durable decisions under `.agents/project/`; no generic style guide there. Report material conflicts before edits.
- Preserve human-authored documents unless their update/migration is requested. Reference existing sources instead of duplicating, moving, deleting or rewriting them automatically.

## Index and documents
- `.agents/project/INDEX.md` is the discovery entry point for agent-maintained project context: a short table of document path, purpose and concrete read conditions (domains/contracts/operations). Table paths are relative to `.agents/project/`; paths into the implementation are Unity-project-root-relative and explicitly identified. No implementation details, exhaustive asset/file inventories or task history in the index.
- If absent, create a minimal index and useful context when introducing a substantial domain or recording confirmed missing knowledge that obstructs understanding. Cover only inspected systems; do not scan/document the whole project or create empty placeholders.
- Register every actual context document; remove stale entries when deleting/consolidating. Load only matches, expanding for discovered dependencies. No blanket read-all conditions.
- ARCHITECTURE.md: cross-domain responsibilities, entry point/public contract paths, dependency direction, composition roots, initialization and reference implementations. Read for boundaries/wiring/cross-domain behavior, not every local fix.
- DOMAIN_<Name>.md: concise domain purpose/boundaries, owned code/asset roots, entry point/public contract paths, dependencies/direction, initialization/teardown and resource ownership, key scenarios/invariants, essential scene/prefab/configuration references, setup and focused verification where relevant. Include coupled visual/audio behavior when needed to prevent regressions and clarify non-obvious exclusions. Reference authoritative sources instead of copying them. Read for that domain.
- VALIDATION.md: verified commands/procedures, prerequisites, available tooling and limits; read for relevant checks/tooling changes. Record established Unity/MCP workflows and fallback constraints when reusable, not transient ports, session IDs or machine-specific paths. Never invent commands or assume a previously available tool is still available.
- Additional cross-cutting documents only for substantial reusable context, with descriptive names/specific read conditions.
- No per-class/method/task documents or empty placeholders. Split only for independently useful responsibilities; document a substantial new domain or missing context that obstructs understanding, not every helper folder.

## Size limits and conditional decomposition
- Apply these limits to agent-maintained project context and project rule Markdown files, including referenced subdocuments. Count all Unicode characters (including whitespace) and physical lines. Before appending, check the affected file's current size; check final sizes after editing. Inspect affected files only, not the whole repository.
- Split at more than 9,000 characters OR 150 lines when independently useful topics can be separated. Hard limit: 12,000 characters OR 200 lines per file. Before exceeding either hard limit, reorganize the affected content in the same task; do not merely warn or defer. A cohesive file above the split threshold may remain only below both hard limits.
- Keep INDEX.md and routing-only documents within 6,000 characters AND 80 lines. Keep root AGENTS routing concise under the same limits when its maintenance is authorized. Move detail out, not essential global constraints. Do not create a chain of indexes to evade the limit.
- Split by actual domain/subdomain, contract or operation (for example player combat, movement, or location transitions), not numbered chunks, arbitrary line counts or one document per class. First remove duplication/stale content without losing valid requirements. Do not shrink by deleting constraints, stripping necessary examples or compressing text into unreadable lines.
- Leave only shared constraints and a short routing table in the parent: relative child path, purpose and concrete read conditions. Link each optional child directly from the discovery parent; avoid nested routing chains. For context, register every resulting context document in .agents/project/INDEX.md. For rules, update their existing AGENTS/rule router; do not put generic rules into project context.
- Read a child only when the task touches its stated responsibility, contract or operation; expand when inspected dependencies make it relevant. Never use "read all children", "any code change" or equivalent blanket conditions for specialized detail. Shared constraints remain mandatory; conditional routing must not hide requirements applicable to the current task.
- Move each requirement/fact to one authoritative place and replace old text with a conditional link; no copied full sections or automatic recursive inclusion of all linked content. If a required selection remains too large for the caller's known context budget, refine routing or report the blocker; never silently truncate or omit applicable requirements.
- Preserve human-authored content unless its update/migration is authorized. If an untouched protected document prevents compliance, report its path, measured size and proposed split rather than modifying it silently. For authorized splits, preserve meaning and repair affected incoming links/read conditions in the same task.
- Before completion, verify affected sizes, link targets, selective routing and preservation of requirements; briefly report material splits. Use existing lightweight tooling or direct checks, without introducing a repository-wide scanner or LLM call.

## Maintenance
- Record concise contracts, source paths and non-obvious decisions, not source copies, exhaustive API/file lists, chat transcripts or repeated rules.
- Update only affected documents and index entries when domains, responsibilities, source/asset paths, contracts, dependencies, lifecycle or setup change. Register new context documents and repair/remove entries for moved/deleted documents in the same task. Small fixes without context changes require no documentation rewrite.
- Before completion, verify affected index targets and documented implementation paths exist, read conditions remain selective, and key claims match the final code/assets. Prefer an existing lightweight link/context check; manual checks suffice if none exists. Do not add an LLM call, repository-wide scanner or validator solely for a small documentation edit.
- Add confirmed details incrementally; distinguish facts/assumptions/proposals and verify important claims against code. Follow DOCUMENTATION_RULES for language/security.
- For long work, maintain one separate progress document only if requested/required; exclude it from default reads. Do not create status files for small tasks.

## Relationship to skills
- Keep reusable procedures in `.agents/skills/` under SKILL_MAINTENANCE_RULES. Context documents retain architecture, contracts, setup and verified tooling facts; link to relevant procedures without duplicating steps. The project INDEX indexes context documents, not every skill/resource.
